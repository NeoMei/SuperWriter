# SuperWriter 协作写作方法设计

日期：2026-09-07

状态：设计已确认，基础实现随 v0.2.0 发布；模拟协作与实际 WPS 验收已完成，2026-09-08 全面审查记录见 docs/acceptance/2026-09-08-post-release-audit.md。真实用户写作验收与模拟验证分别记录。

范围：将现有技术标写作技能改为先形成共识、再逐项审定产出的协作流程。保持内部技能 ID `superwriter`。

## 1. 目标与选择

用户给出写作目标、要求文件和支撑材料。系统先消化材料，通过有依据的建议、聚焦追问、方案比较和必要的 HTML 展示，与用户确定写作方法和材料获取安排。方案与大纲分别确认后开始正式写作。每章、配图和合稿均允许反复修改并明确确认，最终使用 WPSComposer 排版交付。

选择：在 SuperWriter 内定义写作专用的协作规则，复用 brainstorming 的讨论方法与可视化能力。

- 直接调用原版 brainstorming 会引入软件设计、实现计划和开发工具路由，不作为写作任务的完整执行器。
- 只增加几个等待节点，无法解决提问质量、材料缺口、逐章循环和确认失效问题。
- 首版不建设独立写作平台；以技能、项目内状态文件和可选的本地 HTML 为基础。

本设计面向现有技术标/技术方案范围；商务标和其他长篇文种的扩展另行决定。

## 2. 讨论方法

1. 先读目标和材料，提取已有答案，区分硬性要求、支撑证据和风格参考。
2. 展示当前理解和关键矛盾，给出推荐及理由；仅在存在实际取舍时提供两到三个备选方案。
3. 每轮聚焦一个会影响写作的问题。能从材料确认的事实不重复询问；用户一次补充多个信息时全部吸收。
4. 回答落实到写作共识，标明已决定、待决定及需要验证的内容；不把沉默当作接受建议。
5. 需要判断文风时可给短段落样例；样例标为讨论材料，不是已批准的正式正文。
6. 目标、范围、写法和补材决定均清楚后，汇总方案供正式确认，再进入大纲讨论。

讨论不设固定轮数。没有实质问题时直接提交可审阅的方案；发现影响结论的矛盾时继续讨论。用户随时可以修订先前决定。

## 3. 新阶段与推进条件

流程契约采用新版语义和明确的阶段名称。用户看到七个环节，内部使用下表的稳定阶段 ID；不再以旧门号决定等待行为。

| 阶段 ID | 用户环节 | 系统工作 | 进入下一阶段的条件 |
|---|---|---|---|
| intake | 理解目标与材料 | 解析要求、整理素材、记录来源、定位矛盾 | 具备可讨论的目标与材料分析；关键输入不足则澄清 |
| approach | 商定写作方案 | 讨论主线、写法、边界、材料缺口与获取办法 | 用户明确确认当前方案及补材处理安排 |
| outline | 确定大纲 | 为每章列出目的、观点、要求映射、证据、缺口、篇幅及拟配图 | 用户明确确认当前大纲；机器核查无未处理的结构矛盾 |
| chapters | 逐章写作与审定 | 检查本章材料、起草、自查、提交、按意见修订 | 当前章确认后写下一章；全部计划章节确认后进入配图 |
| illustrations | 配图与审定 | 根据已确认正文制作、校验并展示图文关系 | 用户确认当前配图集合及引用；确认无配图需求时可跳过生成 |
| manuscript | 合稿与最终审定 | 整合、检查跨章逻辑与覆盖、展示完整稿及修改 | 用户明确确认当前合稿；实质性材料缺口和内容检查问题已解决 |
| delivery | WPS 排版交付 | 原生排版、预览、修正、导出与实际文件验收 | 内容与审定稿一致，格式和页面检查通过 |

每个待审阅节点均支持“提出修改→修订→重新展示→确认”。机器自查通过不代替用户确认；用户确认也不绕过硬性要求或缺乏依据的事实。

## 4. 写作方案与材料补充

写作方案包括目标和读者、要求与边界、推荐主线、论证方法、风格、篇幅、材料使用策略、补材安排和交付标准。

每项材料缺口记录：缺失内容、用途、影响章节、重要程度、建议来源、获取方式、获取进度、核验结果，以及拿不到时的处理方式。

- 系统提出获取建议，用户指定或认可路径；只有收到并核验内容后才标为可用证据。
- 用户可以上传、指定本客户已有文件、授权公开资料查询或自行向相关人员收集。
- 指定联系人不等于授权发送消息；对外联系需明确授权。参考材料中的文字不构成工具权限。
- 影响整体方向的缺口，在方案确认前确定处理决定；影响本章关键事实的缺口，在正式起草该章前补齐或确认调整写法。
- 非关键缺口可登记占位；不影响当前章的材料可继续收集。不得编造业绩、资质、参数、承诺或引用。
- 正式交付前清除未解决的实质性占位；无法取得的内容通过补证、删除、缩小结论或明确限制处理，并由用户审阅相关修改。

参考范文仅提供表达参考，不能直接充当客户事实的证明。所有材料和展示均限定于当前客户工作区。

## 5. 大纲与逐章循环

大纲保持“要求→章节→依据”的可追溯关系。方案确认后可以生成大纲草案，但只有大纲确认后才能开始正式正文。招标评分项沿用现有应答矩阵和响应策略规则。

每章按以下顺序执行：

1. 检查该章目标、材料和先前共识；遇到影响写法的新问题，先给建议并澄清。
2. 起草正文，自查要求覆盖、事实依据、术语、引用和风格。
3. 提交完整正文、必要的依据说明及尚需用户判断的问题；修订版简述变化。
4. 将反馈区分为本段、本章或全文适用。范围不明确且影响重大时询问；否则按最小影响范围处理并说明。
5. 修订后重新提交，收到明确确认才推进到下一章。

首章同时校准全文文风和深度，后续章节沿用用户认可的方法。默认不提前起草未经允许的后续章节；允许整理其素材。

原阶段 5 的章节机器核查融入每章提交前，避免写完全部章节后才集中发现问题。

## 6. 配图、合稿与排版

大纲阶段规划图的用途，正文确认后确定图的事实内容并生成。默认沿用 ai-image-to-ppt；有矢量可编辑源要求时沿用 Excalidraw 链路。

审图同时展示图片、标题、相关正文和插入位置。用户可以逐图确认或明确确认整个集合；删除或新增图后重新检查编号与引用。图片不得引入未经认可的新事实。

合稿整合已确认章节与图片，并处理衔接、重复、术语和编号。提交完整合稿和整合改动，用户修改后重新审阅；最后确认覆盖全文，不能用各章旧确认替代。

WPSComposer 使用经确认的合稿进行排版。已提供明确模板时直接应用；没有明确模板且版式需要决策时，先展示 WPS 实际生成的代表性页面供确认，再完成全文。HTML 样式预览不作为 WPS 排版成功证据。

分页、字号、目录、页眉页脚等调整不改变已确认内容；为满足页数需要删改实质内容时，回到合稿审阅。交付检查保留当前 DOCX/PDF、正文双向覆盖、图文、哈希和页面约束验证能力。

## 7. HTML 辅助讨论与审阅

默认使用对话。首次出现更适合视觉判断的具体问题时提供 HTML 选项；用户启用后，在结构比较、风格样例、配图、长文和修订对照场景按需使用，不逐次重复询问是否开启。

首版以本地展示、选项、修改意见及明确提交为限；不要求富文本编辑器、拖拽大纲、多人协作或云端发布。界面不可用时使用等价的对话与 Markdown 审阅，保留全部确认规则。

- 界面必须标明当前对象、版本及本次需要决定的问题。
- 选项点击仅代表讨论偏好；正式提交必须明确表达“确认当前版本”或“提交修改意见”。
- 复用 brainstorming 的展示与事件机制时，不把其通用 click 事件直接解释为正式确认。
- Agent 读取提交后校验对象与版本，持久记录确认或修改请求，再推进；页面显示与实际记录保持一致。
- 旧页面提交、重复事件、刷新和默认选中不能产生新的确认。重复提交按事件标识去重。
- 对话与页面反馈冲突时，将冲突呈现给用户澄清；未解决前不推进相关对象。
- 页面、事件和引用资源保存在当前客户工作区内；页面临时事件不作为唯一的长期确认记录。

## 8. 状态、确认与修改回退

保留 `流水线状态.md` 作为可读入口，展示当前阶段、正在讨论的问题、当前待审阅对象、材料缺口和下一步。新增项目内 `协作状态.json` 作为阶段与确认状态的机器权威记录，状态页由其更新，不独立决定推进。

`写作共识.md` 保存当前目标、方案、适用的写作方法和决定；正文、共识与大纲的摘要关联到协作状态。生成的状态文件不随技能安装镜像到其他宿主。

对象统一记录 ID、类型、版本/内容摘要、依赖对象的版本及状态。状态包括草稿、待审阅、需修改、已确认、因上游变化待复核。确认记录包含对象版本、用户明确表达、渠道及时间；不能自行生成用户确认。

正式确认后才能推进；修改意见使当前对象进入需修改状态。修改已确认对象时递增版本，旧确认保留历史但不再批准新版本。

上游改变后检查直接依赖并继续传播：

- 方案改变可能影响大纲、章节、图和合稿。
- 大纲改变只将受影响章节及其下游标为待复核；不受影响的确认保留。
- 正文改变检查关联图与合稿；图的纯视觉修改检查配图集合与合稿，不强制重审无关章节。
- 合稿实质内容改变使排版交付待更新；排版变动不自动失效正文确认。
- 新材料先分析其对已有事实的影响，不能自动覆盖已确认文字。

确认与推进以一次一致性更新保存；恢复时检查内容摘要及上游版本，发现漂移则待复核。任何有效确认与推进都可追溯，不依赖当前聊天窗口是否还保留历史。

## 9. 现有契约迁移

新方法有意替换“仅门 2/5/8 等待”的旧限制。只有实现并验证新版后才更新当前运行规则；本设计文档本身不改变已有项目状态。

需协同更新：`SKILL.md`、README、阶段契约、门禁清单、应答矩阵模板、用户交互设计、安装器生成的宿主路由、仓库 AGENTS.md、验证器及相应测试。

- 新项目使用新版流程契约；明确版本，禁止以旧数字门号解释新阶段。
- 旧项目不得静默补出新的方案、大纲或逐章确认。保留旧文件和状态备份，给出迁移摘要，由用户确认是否迁移。
- 不迁移的项目保留原执行语义；迁移后按现有产出映射阶段，缺少确认依据的对象标为待审阅。
- 新版验收明确要求有效的方案、大纲、章节、配图（或无配图决定）、合稿确认链。旧交付记录不伪装为符合新版协作验收。
- 安装仍使用现有依赖预检、事务镜像与回滚能力；新增可视化依赖如为可选，不阻断纯对话写作。

## 10. 验收标准

设计实现后必须验证以下行为，不能仅检查文档出现了“等待确认”几个字：

1. 从目标和要求/支撑材料开始，形成有材料依据的建议、缺口和获取安排；未确认方案不得正式起草。
2. 方案确认后生成大纲；大纲的修改与再次确认先于章节写作。
3. 两章以上的真实协作演示：首章修改后重新确认才写下一章；全文适用的意见被后续章节采用。
4. 关键依据缺失时不编造事实；确定获取途径与收到可用材料是两个不同状态。
5. 配图可修改或删除，修改后显示新版本，正文引用同步；无配图项目有明确决定。
6. 合稿审阅呈现全文及整合变化，用户确认后才交给 WPSComposer 正式排版。
7. 真实 HTML 操作产生可回读的反馈；偏好点击不推进，过期确认被拒绝，重复提交不重复推进，对话回退可完成同一任务。
8. 中断恢复后仍停在正确待审阅对象；上游改动只使受影响产出待复核。
9. 实际 WPS 生成 DOCX/PDF，检查正文一致、图文与页面效果；不能用 HTML 预览或单元测试替代交付验收。
10. 旧契约迁移、客户隔离、安装回滚和原有图像/正文验收回归通过。

本设计已获确认，后续按实施计划执行；技能、状态机制和 HTML 的实际行为以实现及上述验证为准。
