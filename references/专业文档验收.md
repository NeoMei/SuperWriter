# 专业文档验收（protocol v2）

研究报告、白皮书和技术方案可显式选择 `professional`。在 brief 对象的
`metadata.document_type` 与版本 2 验收清单的 `document_type` 中同时填写
`professional`。省略字段仍按 `tender` 验收；删除评分表不会切换类型。
旧版本 1 验收不支持该字段。

写作方案必须通过 `dependencies` 绑定当前 brief 版本。需求说明就是 brief
对象登记的文件，文件摘要及其依赖链沿用协作状态的漂移检查；大纲仍是
经用户确认的项目根目录 `大纲.md`。不要在交付时另造未审阅的需求表。

在需求说明中写入以下表格，并在大纲中原样列出作为需求矩阵。表头固定，
“内容要求”是应当实际出现在相应章节中的内容锚点，至少含四个有效字符。
使用具体结论、主题句或必须保留的陈述；此检查确认文本覆盖，不判断事实真伪。

| ID | 内容要求 | 章节 |
| --- | --- | --- |
| purpose | 分析需求变化原因 | findings |
| delivery | 说明实施验证方法 | methods |

ID 可以使用通用、非空、无空白或竖线的标识。验收清单 `points` 按表格顺序
列出 ID，`point_chapters` 绑定主章节，章节条目 `points` 包含对应 ID。
章节 `number` 在专业文档中是稳定章节键（如 `findings`），不强制数字编号。
正文仍需有 Markdown 标题；其顺序必须匹配已确认大纲的 `chapter_order`。

无需在成文中保留需求 ID 时，把表格 ID 填为 `-`，并显式使用空 `points`
和空 `point_chapters`。即使没有 ID，也必须列出内容锚点并覆盖每个声明章节。
`required_terms` 可以是空数组；有值时仍逐一检查导出文本。

验收继续检查所有章节、配图集合或无图决定、合稿确认及实际输出。合稿必须
按声明章节顺序保留章节内容；DOCX 和 PDF 必须覆盖合稿内容并通过现有 WPS
元数据、图片、分页与 A4 页面检查。测试使用合成容器不代表实际 WPS 验收。

模板见 `非投标验收清单模板.json`。填写当前 revision、文件路径和真实摘要，
然后运行 `python scripts/verify.py --acceptance-dir <项目绝对路径>`。
