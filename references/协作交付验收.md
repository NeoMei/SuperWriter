# 协作交付验收

新版项目的 `验收清单.json` 使用 `version: 2`，并将 `pipeline` 精确绑定验证时的 `协作状态.json` revision。验收器只做验证，不写入完成事件。旧项目继续使用 v1 清单；已有 `协作状态.json` 的项目不得降级为 v1 验收。

验收器的 Python 环境须按仓库 `requirements.txt` 安装依赖（`python -m pip install -r requirements.txt`；macOS 可用 `python3`）。PDF 元数据、图片和原生长文检查使用 PyMuPDF，图片解码使用 Pillow，SVG 栅格化使用 resvg-py，不依赖 macOS 系统命令。验收同时核对 DOCX 嵌图与 PDF 页面实际绘制的图片像素；仅保留图题、未绘制的图片资源或替换后的图片不能通过。此依赖不自动安装。

## 交付顺序

1. 将当前审定合稿登记为 `manuscript`，路径必须是项目根的 `合并稿.md`，并取得当前版本的明确用户确认。
2. 在导出前创建独立的 `delivery` 草稿对象。该对象的文件是交付报告或输入记录，不得使用 `协作状态.json` 或 `验收清单.json`；依赖精确绑定当前 `manuscript` 版本。
3. 用 WPSComposer 从当前合稿生成 DOCX 和 PDF。将清单的 `pipeline.state_revision` 设为此时状态的当前 revision，并填入当前合稿、章节、配图和输出路径。
4. 从已安装 skill 根运行 `python3 "$SUPERWRITER_SKILL_ROOT/scripts/verify_acceptance.py" "<项目目录>"`（Windows PowerShell 使用 `python "$env:SUPERWRITER_SKILL_ROOT/scripts/verify_acceptance.py" "<项目目录>"`）。只有这次完整验证返回 PASS，才能准备 `record_delivery` 事件。
5. 计算已通过验证的 DOCX/PDF 实际 SHA-256，在项目内写入事件 JSON，再用 Agent CLI 单独提交：

```bash
python3 "$SUPERWRITER_SKILL_ROOT/scripts/collaboration_state.py" apply \
  --project "<项目目录>" \
  --event-file "<项目目录>/record-delivery.json" \
  --expected-revision <第一次验证的 revision>
```

事件必须使用 `channel: "agent"`，绑定当前 `delivery` 的 ID、版本和摘要，并在 `payload` 中记录当前 `manuscript` 摘要以及 DOCX/PDF 的项目内相对路径和实际摘要。

6. CLI 成功后，在同目录创建新的临时清单，仅将 `pipeline.state_revision` 刷新为 CLI 返回的新 revision；对临时文件 `flush` 和 `fsync`，再以原子替换覆盖 `验收清单.json`。不接受旧 revision 宽限。
7. 再次运行同一验收命令。最终 PASS 必须同时证明当前 revision、`verified` delivery 的 `record_delivery` 事件、合稿摘要、DOCX/PDF 路径与实际摘要完全一致。

如果 CLI 已成功而清单原子刷新失败，停止交付。重新读取当前状态和已记录事件，核对输出字节后显式修复清单 revision，然后执行最终验证。不得修改已记录的事件，也不得利用旧 revision 例外绕过修复。

## 投标文件结构核对

投标项目在上述步骤 1 的合稿确认前核对合稿结构，在步骤 3 导出后、步骤 4–5 的验证与完成记录前，核对实际 DOCX/PDF。当前验收器检查文件内容和协作绑定，不会读取招标原文判断格式合规；程序 PASS 不代替本项。代理必须逐项核对并将结果写入 delivery 报告，全部通过后才能记录完成，无需另增一个人工批准事件。

依据为当前 outline 正文中绑定摘要的完整结构约束表，以及该表引用的已核验招标文件及适用补遗。检查规定标题、编号、顺序、层级、分册、必填表格字段、格式和附件；目录与正文分别核对。工具默认样式和自动编号不能覆盖招标格式。导出工具无法保留规定格式时记录阻塞并修复导出，不以“内容都在”放行。

报告记录核对日期、当前 outline 和 manuscript 的 ID/版本/SHA-256，以及实际 DOCX/PDF 路径和 SHA-256，并填写：

| 结构 ID | 来源版本及页码/条款 | 规定内容 | 合稿位置 | DOCX 正文/目录/表格位置 | PDF 页码及位置 | 结果（通过/不通过/待核验） | 差异与修复证据 |
|---|---|---|---|---|---|---|---|
| S01 | 填写来源 | 填写要求 | 填写定位 | 填写定位 | 填写定位 | 待核验 | 填写证据 |

无评分的必需部分也要核对；外部提供部分未取得时不能把完整投标文件记为交付完成。若本次仅交付一个指定分册，明确分册范围及外部部分状态，不把分册完成表述为整套标书完成。

核对报告须在记录完成前通过现有事件写入 delivery 对象当前版本与摘要；如该对象此前已登记为草稿，用 agent 通道的 `put_object` 事件登记新草稿版本（version 加一、status 为 draft、重算报告 SHA-256、依赖绑定当前 manuscript），不修改已登记字节而保留旧摘要。报告登记会增加状态 revision：登记后重新读取协作状态，将清单 `pipeline.state_revision` 刷新为当前 revision，再执行步骤 4 的首次验证；步骤 5 使用该最新 revision 记录完成。上游或输出字节变化后，对新版本重新核对，不能复用旧输出证据。格式问题涉及正文时，回到受影响章节/大纲及合稿修订和重新审阅；仅导出排版问题修复输出并重新验收。

## 配图和无图

`figure_set.metadata.mode` 为 `generated` 时，清单 `figures` 必须按 `figure_ids` 顺序与已确认的图对象逐一对应，`render` 和 `render_sha256` 绑定当前图像字节。figure-set 审阅 Markdown 的当前摘要内必须显式声明：

```markdown
## figure-01
图题: 数据交换总体架构
插入位置: 第二章“接口边界”段后
```

`mode` 为 `none` 时，figure-set 仍必须有独立决定文件和当前版本的明确用户确认，同时清单 `figures` 必须是空数组。

合并稿将图像交给 WPSComposer 时使用其公开 figure directive：

```markdown
:::figure {#fig:review-cycle caption="审阅记录确认循环" width="full" kind="diagram"}
![图 1 审阅记录确认循环](配图/审阅记录确认循环.png)
:::
```

验收器将开闭 directive 视为排版控制语法，仍要求其中的图题出现在 DOCX/PDF 提取内容。其他 `:::` 指令不会被宽泛忽略。

WPSComposer 的公开长文 frontmatter 只能出现在合并稿开头。`title` 是可见标题，DOCX/PDF 均不得遗漏或改写；`heading_numbering: chinese-formal` 会将 H1–H4 分别核对为 `第一章`、`第一节`、`一、`、`（一）` 等按层级递增的原生编号。DOCX 提取器返回的显式 Markdown 标题标记（如 `# 审阅流程与追溯`）只作为 DOCX 标题样式语义核对；PDF 提取内容仍必须包含精确的可见编号。PDF 的单个末尾页码仅在正文已经完整匹配且数字等于 PDF 实际总页数时视为页脚。

原生长文允许按 DOCX 分节字段核对目录页小写罗马页码和正文从 1 开始的阿拉伯页码。页脚必须位于 DOCX 正文下边距之外且严格连续；页眉必须位于正文上边距之外，并同时匹配已批准的标题和 DOCX 页眉。目录按源标题顺序核对，页号必须指向该标题实际所在的正文页。正文中的数字不作为页码删除；无法核对的原生格式继续接受严格正文一致性检查。
