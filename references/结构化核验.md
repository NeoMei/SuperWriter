# 结构化核验与附件生命周期（protocol v2 扩展）

新大纲可在 `metadata` 中同时登记 `chapter_order` 和 `checks`，见 `结构化核验模板.json`。已有 v2 大纲不含 `checks` 时继续兼容，但不获得新增结构、证据和附件自动核验；v1 冻结契约不变。向已有项目增加检查须新建大纲版本并重新审阅，不修改历史事件。

## 投标需求合同

`checks.tender_contract` 是可选的 source-bound 声明。启用时，`source_locator` 必须指向已核验的招标文件、版本和页码/条款；`sections` 按招标原文保存固定标题和顺序，不能把固定章节移动到别的章节。`structure_mode=fixed` 表示不得新增标题，`partial` 只允许 `allow_extensions=true` 且有原文依据的 section 扩展，`free` 也必须记录来源核验结论。

`scoring_items` 按来源评分表顺序登记。评分顺序只用于来源明确允许的扩展位置，不能重排固定章节；每项同时保留精确的 `source_label`、响应 `label` 和显式 `aliases`。例如来源错别字 `报价响应逮度` 与规范写法 `报价响应速度`，必须将其中一个保留为 `source_label`，另一个明确放入 `aliases`，程序不会静默改写来源文本。

`review_index` 是评审索引而不是新的正文结构：每个 `required_item_ids` 必须在 `rows` 中恰好出现一次，标签必须匹配原文或显式别名，并按评分项来源顺序排列。草稿可以使用 `page: null` 或在 notes 中写“待回填”；交付前验收固定调用 `review_index_findings(contract, strict_pages=True)`，所有最终页码必须是正整数。`build_writer_checklist(contract)` 提供按来源顺序的写作者清单，`reverse_evidence_map(contract)` 将每个材料 ID 反查到评分项；二者是审阅辅助，不能替代用户确认、材料真实性核验或交付验收。

本合同记录来源定位和标签，不声称实现原始 `.doc` 解析，也不把 Word-first round-trip 作为流程。当前 canonical source 仍是 Markdown 合稿，经 WPSComposer 生成 DOCX/PDF；`.doc` 转换、人工核对及任何转换缺口必须在来源和交付报告中明确记录。

## 审批绑定

将 checks 对象填写完整，并在大纲正文中放入且仅放入一个同名代码块：

````markdown
```superwriter-checks
{这里填写与 metadata.checks 完全一致的 JSON 对象}
```
````

正文中的 JSON 与 metadata 不一致、缺字段、重复键或被隐藏时，不能提交审阅。使用 `put_object` 登记新的正文摘要、版本及完整 metadata，再走原有 submit_review / approve。修改 checks 会使依赖大纲的章节及下游失效；即使章文字节未变，也不能通过 retain_chapters 保留旧确认。不增加独立批准阶段。状态中的 checks 必须与最近一次 put_object 登记一致，不能通过直接删除或修改状态字段降级检查。

## 标题结构

- `headings` 按正文顺序逐项列出 `{chapter_id, level, title}`，每个 chapter_order 成员至少有一个标题，成员顺序一致。
- `level` 为 1–6 的整数；`title` 是包含规定编号的精确可见标题文本。例如标题为“第一章 技术响应”，不能只登记“技术响应”。
- `heading_mode=exact` 要求每章及合稿 Markdown 的 ATX / Setext 标题层级、文本和顺序完全一致；代码围栏及文首 frontmatter 不作为标题。
- `heading_mode=subsequence` 允许新增标题，但规定标题必须按顺序完整保留。仅在来源允许额外层级/内容位置时采用，并在大纲正文说明依据；程序不判断原文是否真的允许扩展。
- 核验目标是登记的标题及既有 DOCX/PDF 正文一致性。不要把招标目录、OCR 判断、任意排版样式或表格格式说成已自动解析；规定表格和页面仍按交付规则逐项核对。

## 版式规格

`layout` 是 checks 中登记招标文件规定的版式规格及核验状态的字段。protocol v2 投标交付必须填写它；结构为 `status`、`source_locator`、`page`、`page_numbers`、`typography`、`template`：

- `status` 仅接受 verified / unverified / conflict。
- `source_locator` 为非空字符串，记录来源文件版本与页码/条款。
- `page` 登记 `width_mm`、`height_mm`（正数）、`orientation`（仅 portrait / landscape）及 `margins_mm`（top / bottom / left / right 均为非负数）。
- `page_numbers` 登记 `format`（仅 decimal / lowerRoman）与 `start`（正整数）。
- `typography` 登记 `body_font`、`body_size_pt`、`line_spacing`。
- `template` 必须登记模板处理方式。招标文件提供 DOCX/DOTX 格式模板时，先将原文件复制到项目内普通文件路径，并填写 `{"mode":"copy","path":"模板/投标文件格式.docx","sha256":"<实际摘要>","format":"docx"}`；后续 WPSComposer 生成必须以复制件为基准，输出验收会检查模板稳定 OOXML 部件是否保留。已核验没有可直接复用的 Office 模板时填写 `{"mode":"none","reason":"<来源文件、版本、页码及核验结论>"}`。不能只省略字段表示没有模板。

机器核对范围：`page` 读取 DOCX sectPr 的 pgSz/pgMar，按 twips 换算 mm，允许 ±0.5mm 容差，且所有分节一致；`page_numbers` 复用原生长文页码契约；`typography` 读取 DOCX 默认段落样式，并检查正文实际使用的段落样式、继承样式、段落直接格式和字符直接格式。封面、签章、装订及目录格式细节始终人工核对，不由机器核验代替。

`status` 为 unverified / conflict 时，验收报告必须逐项说明未核验或冲突项及原因，不得静默通过。无 `layout` 的旧大纲可以保留历史状态，但 protocol v2 投标交付会被阻断，必须更新大纲并重新审阅；professional 和 legacy-v1 不受本投标版式门禁影响。

## 证据核验字段

`evidence` 的每条记录绑定材料 ID、源文件项目内路径及 SHA-256、章节 ID、原件页码/条目定位、材料记录摘要，以及适用范围与时间。未使用证据时可为 `[]`，不能把缺少强制证明解释为无需证明。

- `material_sha256` 是协作状态中该材料对象的规范 JSON 摘要：`sha256(json.dumps(material, ensure_ascii=False, sort_keys=True, separators=(',', ':')).encode('utf-8'))`。
- `scope` / `required_scope` 均含 `subject`、`product_version`、`period` 三个非空字符串；前者记录核验后的材料范围，后者记录本次要求，两者必须完全一致。不适用的项两边写“不适用”并在审阅正文说明依据。
- `applicability` 仅接受 applicable / not_applicable / unverified；`support` 仅接受 sufficient / partial / none / unverified。用于正式陈述的映射须 applicable + sufficient，且材料 acquired + verified、affected_objects 包含对应章节。
- `as_of` 是来源要求的核验时间基准（YYYY-MM-DD），不是可任意回填的过期豁免。`valid_until` 是 YYYY-MM-DD 或明确不适用时的 null。程序比较有效期是否覆盖 as_of；不会随今天日期推定投标截止日，也不判断财务报表或权利的真实性。
- 源文件变更/丢失、材料记录改动（包括仍保持 verified 的来源改动）会使已批准大纲和依赖失效；恢复旧字节不会自动恢复批准。

核验程序检查的是一致性、已声明的状态和字节，不替代证书出具渠道核验，也不从报告内容自动推断产品适配范围或证据是否充分。source_locator 的语义仍需人工核对。

## 独立附件

`attachments` 是有序的 `{id,path,sha256}` 列表。附件必须在大纲审阅时已准备好并绑定真实字节；尚未备齐时保留草稿，先准备附件再审阅。只支持项目内普通文件，拒绝符号链接、目录跳转、非规范路径、重复 ID 和大小写冲突路径；附件不能冒充状态文件、清单、写作对象或主输出文件。

同一列表还须填写到 v2 验收清单顶层 `attachments` 和 `record_delivery.payload.attachments` 中，三者必须完全一致，包括顺序。无附件为 `[]`；旧清单和旧完成事件省略附件时按空列表兼容，不能用于省略大纲已经声明的附件。

完成前检查真实文件 SHA-256，恢复项目时重新检查。附件删除、替换或链接替换导致大纲/交付失效；字节恢复后仍需修订并重新审阅受影响版本，不能直接恢复 verified。

附件原件的清晰度、页范围、签章及规定表格仍由交付报告逐项核对。扫描页可作为独立附件绑定并做文件完整性验证；这不自动实现 DOCX 内扫描页版式比对。目录、正文引用与附件编号语义仍需人工确认，不能将 hash 一致称为内容合规。

## 执行

使用持久环境的 `runtime.py run collaboration_state.py` 写入事件，`runtime.py run verify_acceptance.py -- <项目目录>` 验证。交付报告更新后重新读取 revision，刷新清单，再执行首次验证、record_delivery、清单 revision 刷新和最终验证。新检查在章节审阅、合稿审阅、记录完成及验收时执行；程序失败不能用聊天确认绕过。
